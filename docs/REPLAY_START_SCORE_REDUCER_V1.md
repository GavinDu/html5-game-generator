# Private diagnostic Go start-score reducer (#471 / Epic #202)

`reduceStartScoreV1` **executes** the strict unpublished Go `game_start→add_score` subset admitted by `supportedPublishedIRProfile`. It processes each rule/action in authored slice order exactly once and emits bounded signed-integer score-after steps. No client-provided state, signed run, timestamp or score is an input. Bad Game IR, unsupported gameplay branches, mismatched type, fraction and missing fields fail with a typed `errStartScoreNotAdmitted`, without partial results. The helper is unexported, has no HTTP endpoint, persistence, native bridge, ranking or verified-state transition.

This is intentionally smaller than a full deterministic game-execution platform. The real preinstalled Pixi JS initializes score=0, emits `game_start` on non-shell v1 boot and executes integer `add_score` actions in rule order; the strict preflight denies other events, recursive score thresholds, physics, input, timers, entities, variables, and experience effects. The diagnostic code does not claim browser-vs-Go conformance: **#469 still requires a real published-style Game IR booted through actual Chromium/WebKit Pixi and compared against Go**. It also has no fixed-tick event queue, seed, game end/win, reliable replay grant or server-owned score/win proof, which remain #428, #382, #457 and #402.

A skeptical review should challenge source-specific assumptions: whether an entityless Game IR boots, whether published `game_start` action order matches this reducer, whether Go `int64` values match JS `Math.trunc` within ±64 million, whether any auth/score trust crosses this package (none should), and whether an unseen action field can bypass admission (the profile denies all non-allowed fields). All six exact-head Go/race, PostgreSQL, Chromium, WebKit, determinism and Playability Kit checks are mandatory to close #471. No physical iPhone/iPad runtime or thermal evidence claimed.
